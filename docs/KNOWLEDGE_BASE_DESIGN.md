# 金融知识库设计与维护机制（v0.1）

> 决策来源：方案 C（产品负责人 2026-10-17 确定），即小型金融知识库 + 来源标注 + 定期维护。
> 知识库内容见 [data/knowledge/knowledge_base.md](../data/knowledge/knowledge_base.md)；实现排在 P4。

---

## 1. 为什么需要知识库

没有知识库时，金融常识问题完全依赖模型自身的知识。输出审查只拦截承诺性表述，**不检查事实**，回答也没有出处。实测中，模型介绍结构性存款时没有提到存款保险 50 万元限额。知识库解决三个问题：

1. **事实可控**：核心概念由人工编写、产品负责人审核，不依赖模型记忆。
2. **出处可查**：回答附依据，客户和审核人员都能核对。
3. **可维护**：法规变化时只改知识库，不改代码和 Prompt。

## 2. 条目结构

每条知识是 `knowledge_base.md` 中的一个三级标题段落，脚本按 `### Kxx` 切分解析：

| 部分 | 内容 |
|---|---|
| 标题 | `### K11 业绩比较基准是什么？是承诺的收益吗？` |
| 元数据 | 状态、版本、核对日期、复核到期、审核人（见 §4） |
| 常见问法 | 同义问法，提升检索召回率 |
| 来源类型 | 法规原文 / 本系统说明 |
| 回答 | 本系统自行编写，100–200 字 |
| 出处 | 引用出处清单编号（S01–S08、S90–S92）+ 条号 + 原文短句 |

**来源类型的诚实原则**：没有监管条文可引用的内容标为「本系统说明」，不冒充法规；由两项规定推出的结论单独注明「综合说明」。

## 3. 运行时：检索与来源标注

```
客户问题 → 话题路由 → 主 Agent → search_documents
                                  ├── 知识库条目（只检索 status = 已审核 且未过期）
                                  └── 虚构产品说明书章节
           → 回答 + 依据标注
```

| 情况 | 界面标注 |
|---|---|
| 依据知识库「法规原文」条目 | 「依据：《业绩比较基准…》知识库 K11 · 《银行保险机构资产管理产品信息披露管理办法》第十三条」 |
| 依据知识库「本系统说明」条目或产品说明书 | 「依据：本系统说明」/「依据：《知岸稳享一年持有》说明书 · 四、产品费用」 |
| 未检索到资料 | 「一般性说明，未引用资料」 |

- 数字类问题（费率、起购金额、期限）走结构化产品数据，不走 RAG。
- 每条回答记录所引用条目的 **编号 + 版本**，写入审计日志，便于事后追溯「当时依据的是哪一版内容」。

## 4. 维护机制

### 4.1 条目元数据

| 字段 | 示例 | 说明 |
|---|---|---|
| 状态 | 已审核 | 草稿 / 已审核 / 待复核 / 已下线 |
| 版本 | 1 | 每次修改内容 +1 |
| 核对日期 | 2026-10-17 | 最近一次对照原文核对的日期 |
| 复核到期 | 2027-04-17 | 默认核对日期 + 6 个月；高频变化的条目可缩短 |
| 审核人 | 产品负责人 | 批准该版本的人 |

### 4.2 生命周期

```
草稿 ──审核通过──→ 已审核 ──到期 / 检查报警──→ 待复核 ──复核通过──→ 已审核（版本 +1 或不变）
  ↑                    │                          │
  └──── 修改内容 ───────┘                          └──确认作废──→ 已下线
```

### 4.3 过期自动降级（关键）

维护和运行时行为挂钩，**即使无人维护，系统也不会把过期内容当权威引用**：

- 检索时只使用「已审核」且未过复核到期日的条目；
- 已过期的条目不作为依据，相关回答降级为「一般性说明，未引用资料」；
- 启动时与检查脚本中都会列出已过期条目。

### 4.4 自动检查脚本 `scripts/check_knowledge.py`

| 检查 | 内容 | 失败时 |
|---|---|---|
| 格式 | 每条都有元数据、来源类型和至少一个出处；引用的 S 编号存在 | 报错 |
| 链接 | 出处链接可访问 | 报警 |
| **原文仍在** | 打开来源页面，确认摘录的原文短句仍然出现 | 报警，并建议将相关条目改为「待复核」 |
| 到期 | 列出 30 天内到期及已过期的条目 | 报警 |

「原文仍在」检查可以自动发现法规修订或页面改版，不依赖人工记忆。可手动运行，也可接入 GitHub Actions 每月自动运行。

### 4.5 事件触发的更新

除定期复核外，以下情况立即更新：

| 触发 | 动作 |
|---|---|
| 监管发布新规或修订 | 检查受影响条目，必要时新增条目 |
| 客户反馈或投诉指出内容有误 | 相关条目改为「待复核」 |
| RAG 评估出现失败用例 | 分析是检索问题还是内容问题 |
| 检查脚本报警 | 按 §4.4 处理 |

### 4.6 变更流程

```
修改条目 → 产品负责人审核 → 版本号 +1、更新核对日期 → 重建检索索引 → 重跑 RAG 评估 → 记入开发日志
```

## 5. MVP 与生产环境

| 方面 | 作品集 MVP | 真实银行环境 |
|---|---|---|
| 内容负责人 | 产品负责人 | 合规部门 + 业务部门 |
| 法规跟踪 | 检查脚本 + 人工关注 | 法规数据库订阅、监管动态专人跟踪 |
| 审核流程 | 单人审核，记入开发日志 | 多级审批、法务复核、留档 |
| 管理工具 | Markdown 文件 + Git 版本管理 | 知识库管理后台、权限控制 |
| 检查频率 | 手动 / 每月自动 | 持续监控 + 定期审计 |

## 6. 实现任务（P4）

1. 解析器：读取 `knowledge_base.md`，校验元数据与出处格式。
2. 检索过滤：只索引「已审核」且未过期的条目。
3. 来源标注：工具返回结构化引用；前端展示依据，可展开查看原文。
4. 审计：回答记录引用条目的编号与版本。
5. `scripts/check_knowledge.py`：格式、链接、原文仍在、到期四项检查。
6. 测试：过期条目不被检索；原文缺失时报警；格式错误时报错。
