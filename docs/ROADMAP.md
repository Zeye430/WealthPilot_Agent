## 3. 剩余阶段任务明细

### P3 产品库与适当性（下一步）

目标：客户完成测评后，能在评级范围内查询、比较产品；不合格的产品进不了候选。

1. **产品要素**：`data/products/products.yaml` 写入 16 个虚构产品；Pydantic 模型校验（费率区间、收益口径、评级取高）。
2. **数据库**：`products`、`product_fees`、`product_return_metrics` 三张表 + Alembic 迁移 + 导入脚本。
3. **说明书生成**：按 PRODUCT_CATALOG §5 模板，从要素生成 16 份 Markdown 说明书（P4 的 RAG 语料）。
4. **适当性规则**：在 Policy Engine 中实现产品级硬过滤（评级、在售状态、起购金额、期限、数据核实），每条产品都返回原因代码。
5. **候选排序**：只在合格产品中排序；权重可配置、可解释（期限匹配、流动性、费用）。
6. **LLM 工具**：`search_products`（内部先过滤）、`get_product_details`（超评级产品只展示条款 + 风险提示）、`compare_products`（收益按口径分列）。
7. **API 与前端**：`/products` 接口（服务端同样过滤）；产品卡片、对比表 UI；「产品浏览」页面上线。
8. **测试**：S04、S04b、S08–S13 及评级取高、口径不混比。

### P4 条款 RAG

目标：客户问条款（投资范围、费用、赎回规则）时，回答有出处、可核对。

1. 按章节切分说明书，`bge-small-zh-v1.5` 生成向量存入 pgvector。
2. jieba + BM25 关键词检索；与向量检索做混合排序（RRF）。
3. `search_documents` 工具：返回「《产品名》说明书 · 章节」引用；前端可展开查看来源原文。
4. 提示注入测试文件 + 防护（文档内容按不可信数据处理）。
5. RAG 评估集 10 条（相关性、忠实度、引用准确、缺失数据处理）。

### P5 需求画像 + 配置情景

目标：跑通原指引的主场景：「100 万，希望年化 5% 左右，风险要小，20 万可能随时要用」。

1. `update_profile` 工具：从对话中记录金额、期限、流动性储备、目标收益，标注来源为「用户提供」；右侧「我的情况」面板实时更新。
2. `simulate_allocation` 工具：组合比例合计必须为 100%，流动性储备单独处理，检查集中度；配饼图。
3. 主场景打磨：解释「低风险、5%、高流动性」三者的取舍，5% 只是目标、不是承诺。

### P6 人工交接

目标：客户可以申请理财经理协助，交接全程有同意、有状态、不虚构。

1. `request_handoff` 工具 + 同意卡片（展示将分享的信息范围）。
2. 状态机：待同意 → 待接单 → 已接单 → 处理中 → 已解决；全部状态变更留痕。
3. 交接摘要：从画像、测评、已讨论产品等结构化数据生成。
4. 理财经理看板 `/rm`：接单、回复、结束；处理期间 AI 暂停回复。
5. 测试 H01–H08。

### P7 评估与交付

1. 端到端评估脚本（真实 Kimi）+ 评估报告。
2. Playwright 自动化测试覆盖主流程。
3. README 门面：截图 / 录屏、架构图、设计要点；演示脚本。
4. `docker compose up` 全量启动验证。
5. 面试讲解材料（见 §5）。

**机动项**（有余力再做）：流式输出、手机端打磨、扩充产品目录。

2. 实现 + 测试；只报告实际运行过的测试结果。

## 5. 面试讲解要点（逐步积累）

- 为什么合规不能只写在 Prompt 里（三道防线）
- 为什么话题路由不承担合规职责（成本与安全分离）
- 为什么关闭 Kimi 思考模式不影响正确性（关键环节交给代码）
- 为什么 RAG 不等于推荐（相似度 ≠ 适当性）
- 为什么金额用 Decimal、计算交给工具
- 收益口径为什么不能混比
- 为什么产品要素是单一数据源（说明书由要素生成）
- 人工交接为什么是状态机而不是一句话术
- 评估集如何量化「零容忍」
